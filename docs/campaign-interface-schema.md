# Campaign interface schema

The repository publishes a versioned, machine-readable description of the
public Soroban interface implemented by `CampaignContract`.

| Artifact | Purpose |
| --- | --- |
| `schemas/campaign-interface.schema.json` | JSON Schema that pins the Campaign interface format. |
| `schemas/campaign-interface-v0.1.json` | Complete v0.1 Campaign interface document. |
| `contracts/campaign-contract/src/lib.rs` | Contract implementation and ABI/interface regression tests. |
| `contracts/campaign-contract/tests/campaign_events.rs` | Runtime tests for exact Campaign event shapes. |

The current `schema_version` is `1` and the current Campaign
`interface_version` is `0.1`.

## Interface coverage

The v0.1 interface describes all 21 public Campaign methods.

For each method it records:

- exact contract method name;
- ordered argument names and Soroban types;
- return structure and types;
- authorization behaviour;
- initialization requirements;
- logical read/write classification; and
- emitted events.

It also records:

- all 27 `CampaignError` variants and numeric discriminants;
- the public methods through which each error can propagate;
- all 12 Campaign event shapes;
- `Campaign`, `ActivationRule`, and `CampaignStatus`; and
- the contract-wide failed-event policy.

## Generated Soroban ABI protection

The interface tests decode Soroban XDR generated by the contract macros and
compare it with `schemas/campaign-interface-v0.1.json`.

The checks cover:

- all exported method names;
- argument names;
- argument order;
- argument types;
- result/value return structure;
- success and error types;
- `Campaign` fields;
- `ActivationRule` fields; and
- `CampaignStatus` cases.

A public Rust change therefore cannot silently alter the generated Soroban ABI
without breaking the committed interface tests.

## Public user-defined types

### `CampaignStatus`

Soroban generates `CampaignStatus` as a UDT union containing three void cases:

1. `Active`
2. `Paused`
3. `Closed`

### `Campaign`

The generated Soroban XDR orders the fields as follows:

| Position | Field | Type |
| ---: | --- | --- |
| 0 | `admin` | `Address` |
| 1 | `allocated_amount` | `i128` |
| 2 | `claimed_amount` | `i128` |
| 3 | `end_time` | `u64` |
| 4 | `funded_amount` | `i128` |
| 5 | `id` | `u64` |
| 6 | `name` | `String` |
| 7 | `per_agent_cap` | `i128` |
| 8 | `reward_token` | `Address` |
| 9 | `start_time` | `u64` |

This intentionally follows generated Soroban XDR ordering rather than the

## Authorization semantics

The interface document records the authorization behaviour implemented by the
contract.

### Direct argument authorization

The authenticated address is supplied directly as a method argument and calls
`Address.require_auth()`.

- `initialize` authenticates `protocol_admin`.
- `create_campaign` authenticates `admin`.
- `verify_and_allocate_reward` authenticates `verifier`.
- `claim_reward` authenticates `agent`.

### Stored campaign-admin authorization

Some methods authenticate the admin stored in the campaign rather than an
address supplied directly to the method.

The contract loads the campaign and calls:

`campaign.admin.require_auth()`

This applies to:

- `fund_campaign`
- `add_activation_rule`
- `pause_campaign`
- `resume_campaign`
- `close_campaign`
- `withdraw_unused_funds`
- `add_verifier`
- `remove_verifier`

The machine-readable interface represents these methods with
`authorization.source = "stored_campaign_admin"` and
`authorization.address_argument = null`.

### No caller authorization

The following current read methods require no caller authentication:

- `available_unused_funds`
- `is_verifier`
- `claimable_reward`
- `agent_total_earned`
- `get_activation_rule`
- `get_campaign`
- `is_initialized`
- `protocol_admin`
- `next_campaign_id`

Missing required authorization is rejected by the Soroban host rather than
returned as a `CampaignError` variant.

## Initialization

`initialize` is the one-time protocol setup method.

It stores:

- initialized state;
- the protocol administrator; and
- `NextCampaignId = 1`.

`is_initialized` may be called before initialization.

Every other public method currently requires initialized protocol state and can
therefore propagate `CampaignError::NotInitialized`.

## Campaign lifecycle

A campaign has three states: `Active`, `Paused`, and `Closed`.

`Closed` is terminal.

### Funding

`fund_campaign` requires the campaign to be:

- `Active`; and
- before `end_time`.

Funding before `start_time` is permitted.

On success, the configured reward token is transferred from the campaign admin
to the Campaign contract.

### Activation rules

`add_activation_rule` requires the campaign to be:

- `Active`; and
- before `end_time`.

Activation rules may be configured before `start_time`.

The current public interface exposes rule creation and retrieval. It does not
expose a public rule-editing or rule-removal method.

### Pause

`pause_campaign` requires `Active` status and current ledger time before
`end_time`. The resulting state is `Paused`.

### Resume

`resume_campaign` requires `Paused` status and current ledger time before
`end_time`. The resulting state is `Active`.

### Close

`close_campaign` accepts an `Active` or `Paused` campaign that has not already
been closed.

A campaign may be closed after its natural `end_time`. This permits
administrative settlement of remaining unused funds.

Once closed, a campaign cannot be resumed.

### Verifier management

`add_verifier` and `remove_verifier` authenticate the stored campaign admin.

Verifier permissions may be managed while the campaign is `Active` or `Paused`,
provided the campaign has not reached `end_time`.

A `Closed` campaign rejects verifier-management operations.
## Reward allocation

`verify_and_allocate_reward` requires all of the following:

- initialized protocol state;
- an existing campaign;
- `Active` campaign status;
- `start_time <= current ledger timestamp`;
- `current ledger timestamp < end_time`;
- a registered verifier;
- authentication by that verifier;
- an existing enabled activation rule;
- a merchant-reference/milestone activation that has not already been processed;
- sufficient unallocated campaign funds; and
- compliance with the optional per-agent cap.

`per_agent_cap == 0` means no per-agent cap is applied.

Successful allocation:

- increases the agent's claimable reward;
- increases the agent's cumulative earned amount;
- increases campaign `allocated_amount`; and
- records the activation as processed.

Allocation does not immediately transfer reward tokens to the agent. It reserves
campaign funds for a later claim.

## Reward claiming

`claim_reward` authenticates the agent and claims the agent's currently
allocated reward for the specified campaign.

Previously allocated rewards remain claimable after:

- campaign pause;
- campaign closure; and
- natural campaign expiry.

On success:

- the claimable amount is cleared;
- campaign `claimed_amount` increases; and
- reward tokens are transferred from the Campaign contract to the agent.

This separation between allocation and claim is intentional.

## Treasury accounting

Campaign accounting uses four cumulative values:

```text
funded_amount
allocated_amount
claimed_amount
withdrawn_amount
```

Allocated rewards remain reserved for agents even before they are claimed.

Unused funds are calculated as:

```text
funded_amount - allocated_amount - withdrawn_amount
```

Claiming does not make previously allocated funds available for administrative
withdrawal because those funds were reserved when allocation occurred.

`withdraw_unused_funds` is permitted only after the campaign has been `Closed`.

A withdrawal cannot exceed the calculated unused amount.

The implementation uses checked arithmetic and returns accounting errors rather
than silently wrapping integer values.

## Error interface

`CampaignError` currently defines 27 discriminants numbered `1` through `27`.

The versioned interface records:

- variant name;
- numeric discriminant;
- public methods through which the error can propagate; and
- a human-readable description.

Errors originating in private helpers are attributed to the public methods
through which they propagate.

For example:

- `NotInitialized` propagates through `require_initialized`;
- `CampaignNotFound` propagates through `load_campaign`.

The committed regression test protects this mapping from silent drift.

## Events

The contract currently defines 12 logical Campaign events.

| Logical event | Emitted by | On-chain topics |
| --- | --- | --- |
| `init` | `initialize` | `campaign`, `init` |
| `created` | `create_campaign` | `campaign`, `created` |
| `funded` | `fund_campaign` | `campaign`, `funded` |
| `rule_added` | `add_activation_rule` | `campaign`, `rule`, `added` |
| `paused` | `pause_campaign` | `campaign`, `paused` |
| `resumed` | `resume_campaign` | `campaign`, `resumed` |
| `closed` | `close_campaign` | `campaign`, `closed` |
| `unused_withdraw` | `withdraw_unused_funds` | `campaign`, `unused`, `withdraw` |
| `verifier_added` | `add_verifier` | `campaign`, `verifyr`, `added` |
| `verifier_removed` | `remove_verifier` | `campaign`, `verifyr`, `removed` |
| `reward_allocated` | `verify_and_allocate_reward` | `campaign`, `activate`, `reward` |
| `reward_claimed` | `claim_reward` | `campaign`, `reward`, `claim` |

`verifyr` is the intentional on-chain topic spelling used to satisfy Soroban
short-symbol constraints. SDKs and indexers must use the actual topic value.

Logical interface labels such as `rule_added` are not single on-chain topics.
The complete ordered `topics` array is the event identity.

The Campaign event suite executes every current successful event-producing
operation and asserts the exact topic and payload shape.

Failed calls do not emit Campaign events.

## TTL behaviour

The Campaign contract actively extends Soroban storage TTLs.

Instance state includes:

- initialized state;
- protocol administrator; and
- next campaign ID.

Persistent state includes:

- campaigns;
- activation rules;
- verifier permissions;
- processed activations;
- claimable rewards; and
- cumulative agent earnings.

Public reads can refresh storage TTL while remaining logical `read` methods.
The interface `mutability` field describes business-state semantics rather than
ledger TTL maintenance.

## SDK consumption

SDK consumers should:

1. Reject unsupported `schema_version` values.
2. Match `interface_version` against the contract interface supported by the SDK.
3. Invoke exact symbols from the `methods` collection.
4. Preserve argument order using each argument's `position`.
5. Encode values using the documented Soroban types.
6. Treat `i128` amounts as integer values rather than floating-point values.
7. Decode `kind = "result"` methods using their `ok` and `error` types.
8. Treat `is_initialized`, which returns `kind = "value"`, separately from Result-returning methods.
9. Use `authorization.source` to distinguish direct argument authorization from stored campaign-admin authorization.
10. Decode public UDTs using the committed generated-XDR field/case ordering.
11. Filter events using the complete ordered `topics` array.
12. Decode event payload fields using their documented positions.

## Updating the interface

A contract change affecting any of the following must update the Campaign
interface artifacts in the same PR:

- exported method names;
- argument names;
- argument ordering;
- argument types;
- return structure;
- public UDT structure;
- authorization behaviour;
- initialization requirements;
- lifecycle semantics represented by the document;
- error variants or discriminants;
- error propagation;
- event topics; or
- event payloads.

For an interface-breaking change:

1. increment `interface_version`;
2. add a new versioned interface document rather than silently rewriting an old compatibility contract;
3. update the JSON Schema constraints;
4. update the generated-spec and semantic regression tests;
5. update SDK compatibility work; and
6. document the change in the same PR.
